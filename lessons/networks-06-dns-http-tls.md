# DNS, HTTP, HTTPS и TLS

## Что даст эта глава

После чтения ты сможешь:

- объяснить путь от доменного имени до IP-адреса;
- различать основные DNS-записи;
- читать простой HTTP-запрос и ответ;
- понимать назначение TLS и сертификата;
- разделять проблемы DNS, TCP, TLS и HTTP.

## Полный путь браузера

Пользователь вводит:

```text
https://example.com/
```

Упрощённая последовательность:

1. Браузер разбирает URL.
2. DNS определяет IP домена.
3. Система выбирает маршрут.
4. Определяется MAC ближайшего узла или шлюза.
5. Устанавливается транспортное соединение.
6. Выполняется TLS handshake.
7. Браузер отправляет HTTP-запрос.
8. Сервер возвращает HTTP-ответ.
9. Браузер загружает дополнительные ресурсы.

Фраза «сайт не работает» может означать проблему на любом из этих шагов.

## DNS

DNS связывает доменные имена с данными. Самый известный случай — получение IP-адреса по имени.

```text
example.com → 93.184.216.34
```

Но DNS хранит не только адреса.

## Основные DNS-записи

| Тип | Назначение |
|---|---|
| A | IPv4-адрес имени |
| AAAA | IPv6-адрес имени |
| CNAME | псевдоним другого имени |
| MX | почтовые серверы домена |
| NS | авторитетные DNS-серверы зоны |
| TXT | произвольные текстовые данные и политики |
| PTR | обратное соответствие IP имени |
| SOA | основные параметры DNS-зоны |

Пример запроса:

```bash
dig example.com A
```

Краткий ответ:

```bash
dig +short example.com
```

Посмотреть DNS-серверы системы:

```bash
cat /etc/resolv.conf
```

В современных системах файл может управляться NetworkManager или `systemd-resolved`, поэтому ручные изменения могут быть перезаписаны.

## Как выполняется DNS-разрешение

Обычно приложение обращается к настроенному рекурсивному резолверу. Тот может иметь ответ в кэше. Если ответа нет, он проходит иерархию DNS.

Упрощённо:

```text
Клиент
  → рекурсивный DNS
  → корневой сервер
  → сервер зоны верхнего уровня
  → авторитетный сервер домена
  → ответ клиенту
```

Клиент обычно не выполняет всю цепочку сам: эту работу делает рекурсивный сервер.

## Кэширование и TTL

DNS-ответ имеет TTL — время, в течение которого его можно хранить в кэше.

Это ускоряет работу и уменьшает нагрузку, но после изменения записи пользователи могут некоторое время получать старый ответ.

DNS TTL и IP TTL — разные понятия:

- DNS TTL — время кэширования записи;
- IP TTL — ограничение числа маршрутизирующих переходов пакета.

## URL

Разберём:

```text
https://example.com:443/docs/page?mode=short#part
```

| Часть | Значение |
|---|---|
| `https` | схема |
| `example.com` | имя хоста |
| `443` | порт |
| `/docs/page` | путь |
| `mode=short` | query string |
| `part` | фрагмент страницы |

Фрагмент после `#` обычно обрабатывается браузером и не отправляется серверу в HTTP-запросе.

## HTTP-запрос

Простой запрос:

```text
GET /docs HTTP/1.1
Host: example.com
User-Agent: ExampleBrowser/1.0
Accept: text/html
```

Первая строка содержит:

- метод `GET`;
- путь `/docs`;
- версию HTTP.

Затем идут заголовки. Пустая строка отделяет заголовки от тела.

Основные методы:

| Метод | Типичное назначение |
|---|---|
| GET | получить ресурс |
| POST | отправить данные или создать действие |
| PUT | заменить ресурс |
| PATCH | частично изменить ресурс |
| DELETE | удалить ресурс |
| HEAD | получить только заголовки ответа |
| OPTIONS | узнать доступные возможности |

Реальное значение определяется приложением. Метод сам по себе не обеспечивает безопасность или права доступа.

## HTTP-ответ

Пример:

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1250
Set-Cookie: session=abc123; HttpOnly; Secure

<!doctype html>
```

Первая строка содержит статус. Затем идут заголовки и тело.

Группы статусов:

| Диапазон | Значение |
|---|---|
| 1xx | информационные |
| 2xx | успешное выполнение |
| 3xx | перенаправление |
| 4xx | ошибка запроса клиента |
| 5xx | ошибка обработки на сервере |

Частые статусы:

- `200 OK` — запрос выполнен;
- `301` или `308` — постоянное перенаправление;
- `302` или `307` — временное перенаправление;
- `400 Bad Request` — сервер не понял запрос;
- `401 Unauthorized` — требуется аутентификация;
- `403 Forbidden` — доступ запрещён;
- `404 Not Found` — ресурс не найден;
- `500 Internal Server Error` — ошибка приложения;
- `502 Bad Gateway` — промежуточный сервер получил плохой ответ;
- `503 Service Unavailable` — сервис временно недоступен.

## HTTP не равен веб-странице

HTTP используется не только браузерами. По нему работают API, обновления, webhooks и взаимодействие сервисов.

Один HTML-документ может вызвать десятки дополнительных запросов:

- CSS;
- JavaScript;
- изображения;
- шрифты;
- API;
- аналитика.

Поэтому загрузка страницы — это не один пакет и обычно не один запрос.

## Что добавляет TLS

Обычный HTTP не обеспечивает конфиденциальность и целостность трафика. HTTPS означает HTTP поверх TLS.

TLS предоставляет:

- шифрование содержимого;
- контроль целостности;
- аутентификацию сервера с помощью сертификата;
- иногда аутентификацию клиента.

TLS не делает само веб-приложение безопасным. SQL-инъекция, слабая авторизация или логическая ошибка остаются возможными даже при правильном HTTPS.

## Сертификат

Сертификат связывает открытый ключ с именем сервера и содержит:

- доменные имена;
- срок действия;
- открытый ключ;
- сведения об издателе;
- цифровую подпись удостоверяющего центра.

Клиент проверяет:

1. Подходит ли имя в сертификате к запрошенному домену.
2. Не истёк ли срок действия.
3. Доверяет ли система цепочке сертификатов.
4. Корректна ли подпись.

Сертификат не доказывает, что сайт честный. Он подтверждает связь ключа с указанным именем в рамках модели доверия.

## Упрощённый TLS handshake

Современный TLS согласует:

- поддерживаемую версию;
- криптографические параметры;
- ключевой материал сеанса;
- сертификат сервера.

После handshake стороны получают симметричные ключи и используют их для эффективного шифрования данных приложения.

Асимметричная криптография помогает установить доверие и ключи. Основной поток данных шифруется симметричными алгоритмами, потому что они быстрее.

## SNI и виртуальный хостинг

На одном IP могут работать несколько HTTPS-сайтов. Во время TLS handshake клиент передаёт имя сервера через SNI, чтобы сервер выбрал подходящий сертификат.

В HTTP/1.1 имя также передаётся в заголовке `Host`.

Поэтому запрос только по IP может вернуть другой сайт или ошибку, даже если порт `443` открыт.

## Полезные команды

Проверить DNS:

```bash
dig example.com
```

Получить HTTP-заголовки:

```bash
curl -I http://example.com
```

Посмотреть подробности соединения и TLS:

```bash
curl -v https://example.com/
```

Проверить сертификат:

```bash
openssl s_client -connect example.com:443 -servername example.com
```

Завершить `openssl s_client` можно `Ctrl + C`.

Для своей Metasploitable:

```bash
curl -I http://192.168.56.20
```

Если веб-сервер доступен, ты увидишь статус и заголовки.

## Как разделять ошибки

Если сайт не открывается, проверяй по уровням.

### Имя

```bash
dig example.com
```

Если ответа нет, проблема может быть в DNS.

### Маршрут и достижимость

```bash
ip route get <IP>
ping -c 2 <IP>
```

### TCP-порт

```bash
nc -vz <IP> 443
```

### TLS

```bash
openssl s_client -connect <домен>:443 -servername <домен>
```

### HTTP

```bash
curl -v https://<домен>/
```

Так ты не смешиваешь ошибку DNS с ошибкой веб-приложения.

## Что важно запомнить

- DNS связывает имена с записями, включая IP-адреса.
- HTTP состоит из запросов и ответов.
- Статус описывает результат обработки запроса.
- HTTPS — это HTTP поверх TLS.
- TLS защищает канал, но не исправляет уязвимости приложения.
- Сертификат связывает открытый ключ с именем.
- Один IP может обслуживать много доменов.
- Диагностику нужно разделять на DNS, транспорт, TLS и HTTP.
