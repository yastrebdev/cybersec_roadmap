# TCP, UDP, порты и сокеты

## Что даст эта глава

После чтения ты сможешь:

- объяснить назначение транспортного уровня;
- сравнить TCP и UDP;
- описать трёхэтапное рукопожатие TCP;
- понимать номера портов и сетевые сокеты;
- читать основные состояния соединений в `ss`.

## Задача транспортного уровня

IP доставляет пакет до компьютера. Но на компьютере одновременно работают браузер, SSH-клиент, DNS-служба и множество других программ.

Нужно определить, какому процессу отдать данные. Для этого транспортные протоколы используют номера портов.

```text
IP-адрес → нужный компьютер
Порт      → нужное приложение на компьютере
```

Два основных транспортных протокола интернета — TCP и UDP.

## Порты

Номер порта — 16-битное число от `0` до `65535`.

Условные диапазоны:

| Диапазон | Назначение |
|---|---|
| `0–1023` | системные и общеизвестные порты |
| `1024–49151` | зарегистрированные сервисы |
| `49152–65535` | динамические или временные порты |

Распространённые значения:

| Порт | Транспорт | Типичный сервис |
|---|---|---|
| 22 | TCP | SSH |
| 53 | UDP/TCP | DNS |
| 80 | TCP | HTTP |
| 123 | UDP | NTP |
| 443 | TCP и иногда UDP | HTTPS, HTTP/3 |
| 445 | TCP | SMB |
| 3306 | TCP | MySQL |

Порт не гарантирует конкретный протокол приложения. На `80` можно запустить SSH, а веб-сервер — на `8080`. Номер порта является сильной подсказкой, но сервис нужно подтверждать.

## Клиентский и серверный порты

Веб-сервер слушает известный порт:

```text
192.168.56.20:80
```

Kali выбирает временный исходный порт:

```text
192.168.56.10:49152
```

Соединение можно представить как пару:

```text
192.168.56.10:49152 → 192.168.56.20:80
```

Ответ идёт в обратную сторону:

```text
192.168.56.20:80 → 192.168.56.10:49152
```

Благодаря временному порту Kali понимает, какому клиентскому процессу вернуть ответ.

## Сетевой сокет

Сокет — программная конечная точка сетевого обмена. В практическом контексте его описывают сочетанием:

```text
протокол + локальный IP + локальный порт
```

Для установленного TCP-соединения также важны удалённые IP и порт.

Один сервер может слушать:

```text
0.0.0.0:80
```

Это обычно означает: принимать IPv4-подключения на порту `80` через все локальные интерфейсы.

Если он слушает:

```text
127.0.0.1:80
```

сервис доступен только с самого компьютера.

Если он слушает:

```text
192.168.56.20:80
```

сервис привязан только к указанному интерфейсу.

## TCP

TCP — протокол с установлением соединения. Он предоставляет приложению упорядоченный поток байтов и пытается обеспечить надёжную доставку.

TCP решает задачи:

- установка соединения;
- нумерация данных;
- подтверждение получения;
- повторная передача потерянных сегментов;
- восстановление порядка;
- управление скоростью передачи;
- корректное завершение соединения.

## Трёхэтапное рукопожатие TCP

Перед передачей данных стороны устанавливают соединение.

```text
Клиент                         Сервер
   | -------- SYN -----------> |
   | <----- SYN, ACK ----------|
   | -------- ACK -----------> |
```

### SYN

Клиент сообщает о желании начать соединение и передаёт начальный номер последовательности.

### SYN-ACK

Сервер подтверждает запрос и сообщает собственный начальный номер.

### ACK

Клиент подтверждает ответ сервера. После этого соединение установлено.

Именно поэтому открытый TCP-порт можно обнаружить по реакции на SYN.

## Подтверждения и повторная передача

TCP нумерует передаваемые байты. Получатель подтверждает, до какого места данные приняты.

Если подтверждение не пришло вовремя, отправитель может повторить передачу.

Приложение получает упорядоченный поток, даже если отдельные IP-пакеты пришли в другом порядке.

Надёжность TCP не означает, что соединение никогда не оборвётся. Она означает, что протокол обнаруживает многие потери и пытается их компенсировать.

## Завершение TCP

Обычное закрытие использует флаги FIN и ACK. Стороны независимо подтверждают завершение передачи.

Флаг RST означает немедленный сброс соединения. Например, закрытый TCP-порт часто отвечает RST.

Полезные флаги:

| Флаг | Назначение |
|---|---|
| SYN | начало соединения |
| ACK | подтверждение |
| FIN | корректное завершение |
| RST | немедленный сброс |
| PSH | передать данные приложению без лишней задержки |

## Состояния TCP

Команда:

```bash
ss -tan
```

может показать состояния:

- `LISTEN` — процесс ожидает входящие подключения;
- `SYN-SENT` — клиент отправил SYN;
- `SYN-RECV` — сервер получил SYN и ответил;
- `ESTAB` — соединение установлено;
- `FIN-WAIT-1` и `FIN-WAIT-2` — локальная сторона закрывает соединение;
- `CLOSE-WAIT` — удалённая сторона запросила закрытие;
- `TIME-WAIT` — система временно хранит информацию о закрытом соединении.

`TIME-WAIT` — нормальная часть TCP, а не обязательно ошибка.

## UDP

UDP не устанавливает соединение и не создаёт надёжный поток. Приложение отправляет отдельные датаграммы.

UDP сам по себе не гарантирует:

- доставку;
- порядок;
- отсутствие дубликатов;
- повторную передачу.

Зато у него меньше служебных действий и задержек.

UDP используют там, где:

- приложение само контролирует повторы;
- важна минимальная задержка;
- допустима потеря части данных;
- удобна модель «один запрос — один ответ».

Примеры: DNS, DHCP, NTP, потоковое аудио, некоторые VPN и современные транспортные протоколы поверх UDP.

## TCP и UDP в сравнении

| Свойство | TCP | UDP |
|---|---|---|
| Установка соединения | Да | Нет |
| Гарантия порядка | Да | Нет |
| Повторная передача | Да | Нет |
| Поток или сообщения | Поток байтов | Отдельные датаграммы |
| Накладные расходы | Выше | Ниже |
| Пример | SSH, HTTP/1.1 | DNS, DHCP |

Нельзя сказать, что TCP всегда лучше. Выбор зависит от требований приложения.

## Как посмотреть сокеты Linux

Все TCP-сокеты:

```bash
ss -tan
```

Только слушающие TCP-сокеты:

```bash
ss -ltn
```

UDP-сокеты:

```bash
ss -uan
```

Показать процессы:

```bash
sudo ss -lntup
```

Параметры:

- `-l` — только listening;
- `-n` — не преобразовывать порты и адреса в имена;
- `-t` — TCP;
- `-u` — UDP;
- `-p` — процессы.

Пример:

```text
LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=700,fd=3))
```

Здесь SSH слушает TCP-порт `22` на всех IPv4-интерфейсах.

## Открытый, закрытый и фильтруемый порт

**Открытый** — приложение слушает порт и отвечает ожидаемым образом.

**Закрытый** — узел доступен, но на порту нет слушающего приложения. TCP часто отвечает RST.

**Фильтруемый** — сетевой фильтр мешает определить состояние. Пакеты могут отбрасываться без ответа.

Эти состояния описывают результат наблюдения, а не вечное свойство порта. Сервис может запуститься или остановиться, а правила firewall — измениться.

## Практическое наблюдение

На Kali открой слушающие сокеты:

```bash
sudo ss -lntup
```

Выбери одну строку и ответь:

1. TCP это или UDP?
2. Какой локальный адрес?
3. Какой порт?
4. На всех интерфейсах доступен сервис или только локально?
5. Какой процесс владеет сокетом?

Создай временный HTTP-сервис:

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

В другом терминале найди его:

```bash
ss -ltnp | grep 8000
curl http://127.0.0.1:8000
```

Останови сервер через `Ctrl + C`.

## Что важно запомнить

- IP доставляет до узла, порт — до приложения.
- Сервер обычно слушает известный порт, клиент использует временный.
- TCP устанавливает соединение и упорядочивает поток.
- UDP передаёт независимые датаграммы без гарантий TCP.
- `0.0.0.0` у слушателя обычно означает все IPv4-интерфейсы.
- `127.0.0.1` доступен только локально.
- `ss` показывает сокеты и состояния соединений.
